# judgpt — 아키텍처 설계 (v0.1, MVP)

> 이 문서는 `docs/REQUIREMENTS.md` §3.1(MVP)의 구체적인 구현 설계다. RAG(§3.2)는 범위 밖 — MVP가 안정화된 뒤 별도 문서(`03-legal-rag-design.md` 예정)로 다룬다.

## 0. 전제 — 하드웨어 제약

이 프로젝트는 예산이 없어 로컬 LLM(Ollama)만 쓴다. 개발 노트북 사양은 i5-13500H, RAM 16GB, 내장 GPU(Iris Xe, 전용 VRAM 없음) — GPU 가속 없이 **CPU 전용 추론**이다. 이게 아래 모든 결정(모델 크기, 응답 지연 허용치)의 상한을 정한다.

## 1. 파이프라인 개요

REQUIREMENTS.md 원안의 1~3단계(전처리/유해표현탐지/문맥분석)를 **하나의 LLM 호출**로 처리한다. 별도 마스킹 모델이나 분류기를 두지 않는다 — 최신 7B급 모델도 지시문을 잘 따르면 마스킹·분류·문맥판단을 한 번에 처리할 수 있고, 파이프라인을 나누면 CPU 추론 1회당 수십 초가 걸리는 상황에서 지연만 배가된다.

```
채팅 텍스트 (파일 또는 stdin)
  ↓
프롬프트 조립 (시스템 프롬프트 + 사용자 텍스트)
  ↓
Ollama 호출 (OpenAI 호환 엔드포인트, response_format=json_object)
  ↓
JSON 파싱 + Pydantic 스키마 검증
  ↓ (실패 시 에러 메시지 포함해 1회 재시도) ↓
사람이 읽기 좋은 리포트 출력 (+ --json 플래그로 원본 JSON)
```

## 2. 모델/런타임

- **기본 모델: `exaone3.5:7.8b`** (LG AI연구원, 한국어 특화 튜닝, Q4 양자화 기준 약 5GB).
- **대안: `qwen2.5:7b`** — repoview 프로젝트에서 이미 검증된 모델. exaone 결과가 기대에 못 미치면 즉시 교체 테스트할 수 있도록 모델명을 코드에 박지 않고 설정값(환경변수)으로 뺀다.
- **판단 이유 — 왜 한국어 특화 모델을 기본으로 하는가:** 이 작업의 핵심은 욕설/성희롱/협박/모욕의 **뉘앙스와 맥락** 판단(반어법, 은어, 거부 이후 반복 등)이다. 범용 다국어 모델보다 한국어 전용 튜닝 모델이 이 판단에서 유리할 가능성이 높다고 보고 기본값으로 선택했다 — 다만 실측 비교 전이므로 확정은 아니다(§9 미해결 질문).
- **판단 이유 — 왜 OpenAI 호환 REST 방식인가:** Ollama는 `/v1/chat/completions` OpenAI 호환 엔드포인트를 제공한다. repoview가 이미 이 방식으로 Ollama를 붙인 전례가 있어(`repoview/agent/llm.py`의 `OllamaLLM`), 같은 패턴을 재사용하면 새로 배울 것 없이 검증된 방식으로 시작할 수 있다.
- **판단 이유 — 왜 7~8B/Q4가 상한인가:** CPU 전용 16GB RAM에서 7~8B Q4 양자화 모델은 약 5GB를 차지하며 실행 가능하지만, 속도는 초당 몇 토큰 수준으로 느리다. 이 도구는 실시간 채팅이 아니라 "붙여넣고 기다리는" 배치 분석이므로 응답당 30~90초는 감수 가능하다고 판단했다. 13B 이상은 이 하드웨어에서 비현실적이다.

## 3. 입력 형식

- 사용자가 그대로 붙여넣은 자유 형식 텍스트. `--file <path>` 인자 또는 stdin으로 받는다.
- "화자: 내용" 형식의 줄 구분을 권장하되 강제하지 않는다 — 모델이 문맥으로 화자를 유추하게 한다.
- 카카오톡 등 특정 메신저의 내보내기 포맷을 자동 파싱하는 기능은 REQUIREMENTS.md §3.3에 따라 이번 범위에서 제외한다.

## 4. 프롬프트 설계

시스템 프롬프트는 다음을 명시한다:
1. 역할: 채팅 텍스트에서 개인정보를 마스킹하고, 욕설/성희롱/협박/모욕/명예훼손에 해당할 수 있는 표현을 찾아 문맥·의도·반복성·공개성을 함께 판단한다.
2. 출력 스키마(§5)를 JSON으로만 응답하도록 강제 — 스키마 예시를 프롬프트에 그대로 포함한다.
3. **법적 고려사항(REQUIREMENTS.md §4) 반영**: "법 조문이나 판례를 언급하지 말 것 — 이 단계는 근거 문서(RAG) 없이 법률 판단을 지어내면 안 된다"는 제약을 명시한다. MVP 산출물은 표현 탐지·위험도까지이며, "적용 가능 법률"/"관련 판례"는 아직 채우지 않는다(REQUIREMENTS.md §3.1).

## 5. 출력 스키마 (Pydantic)

```python
class Expression(BaseModel):
    text: str                # 마스킹 적용된 원문 인용
    type: Literal["욕설", "성희롱", "협박", "모욕", "명예훼손", "성적 발언", "기타"]
    target: str | None       # 대상 (예: "상대방", 특정 지칭 없으면 None)
    risk: Literal["높음", "중간", "낮음"]
    context: str | None      # 반복성/공개성/거부 이후 반복 등 판단 근거가 된 맥락

class AnalysisResult(BaseModel):
    expressions: list[Expression]
```

`disclaimer`(참고용 정보 고지)는 LLM 출력에 맡기지 않고 CLI 출력 단계에서 항상 고정 문구로 붙인다(§7) — 모델이 빼먹거나 문구를 바꿔버릴 여지를 없앤다.

## 6. 신뢰성 — 재시도 전략

로컬 7~8B 모델은 GPT-4o급보다 JSON 형식을 깨뜨리는 빈도가 높다는 전제 하에:
1. Ollama 호출 시 `response_format={"type": "json_object"}`로 형식을 강제한다.
2. 응답을 `json.loads` → `AnalysisResult` Pydantic 검증 순으로 처리한다.
3. `JSONDecodeError` 또는 `ValidationError` 발생 시, 실패한 원본 응답과 에러 내용을 알려주는 메시지를 추가해 **1회만 재시도**한다.
4. 재시도까지 실패하면 빈 결과를 조용히 반환하지 않고 "분석 실패 — 모델 응답 형식 오류"를 사용자에게 명확히 알리고 0이 아닌 종료 코드로 끝낸다.

## 7. CLI 설계

- 실행: `python -m judgpt.analyze --file chat.txt` 또는 `cat chat.txt | python -m judgpt.analyze`
- 기본 출력: REQUIREMENTS.md §2 형식과 동일한, 사람이 읽기 좋은 리포트.
- `--json` 플래그: 검증된 원본 JSON을 그대로 출력(스크립트 연계용).
- 출력 하단에는 항상 고정 문구를 포함한다: "이 결과는 참고용 정보이며 법적 판단이 아닙니다. 실제 법적 대응이 필요하면 변호사와 상담하세요."

## 8. 테스트 전략

- repoview의 `LLM` Protocol + `FakeLLM` 패턴을 그대로 재사용한다 — 테스트는 실제 Ollama를 호출하지 않는다.
- `tests/fixtures/`에 "명백히 문제 있는 대화" 1~2개, "평범한 대화"(오탐 없어야 함) 1~2개 예시 텍스트를 둔다.
- 단위 테스트 범위: 프롬프트 조립, JSON 파싱/검증, 재시도 로직(1차 응답이 깨진 JSON → 재시도 → 정상 JSON을 반환하는 시나리오를 `FakeLLM`으로 재현).
- 실제 Ollama가 설치된 환경에서만 도는 통합 테스트는 `@pytest.mark.integration`으로 분리해 기본 `pytest` 실행(CI 포함)에서는 제외한다 — repoview의 `eval.py`처럼 자동 채점 하네스는 이 단계에서는 과함(YAGNI), 필요해지면 RAG 단계에서 다시 검토한다.

## 9. 범위 제외 (재확인, REQUIREMENTS.md와 동일)

- 법률 RAG (조문/판례 검색) — 2차 확장.
- 카카오톡 등 메신저 포맷 자동 파싱.
- 웹 UI — CLI로 시작, 필요해지면 나중에 얇게 추가.
- 자동 채점 eval 하네스.
