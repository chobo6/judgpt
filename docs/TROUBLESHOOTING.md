# TROUBLESHOOTING

실제 발생한 버그·장애의 근본 원인과 수정 방법을 기록한다. 개발 세션 중 실제로 겪은 것을 시간 순으로 정리했다. 최신 구현이 아래 설명과 다르면 코드가 우선이다.

## MVP 구현 (Task 1-8, 최종 리뷰, PR #1 코드리뷰)

### #1 서브에이전트 dispatch 시 `isolation: "worktree"`를 잘못 넘겨 워크트리가 중복 생성됨

**증상**: Task 1 구현 서브에이전트가 파일은 올바르게(브리프와 완전히 동일하게) 작성했지만, 테스트 실행·커밋을 못 하고 BLOCKED로 끝났다.

**원인**: 컨트롤러가 이미 전용 워크트리(`judgpt-mvp`)를 준비해둔 상태에서, Agent 디스패치에 `isolation: "worktree"`를 추가로 넘겨 별도의 워크트리(`agent-af3242df63c3cb4c0`)가 새로 생성됐다. 서브에이전트가 원래 워크트리로 돌아가려고 `EnterWorktree`를 호출하면서 샌드박스가 잠겼다. (repoview 프로젝트에서도 동일한 실수가 한 번 있었던 패턴 — 재발함.)

**해결**: 컨트롤러가 별도 워크트리에 생성된 4개 파일이 브리프와 바이트 단위로 동일함을 확인한 뒤 올바른 워크트리로 복사, 테스트 실행 후 직접 커밋. 스트레이 워크트리/브랜치는 삭제. **이후 모든 태스크 디스패치에서 `isolation: "worktree"`를 빼고 진행** — 컨트롤러가 이미 전용 워크트리를 관리 중일 때는 이 옵션을 절대 넘기지 말 것.

### #2 `OllamaLLM.call()`이 `None`을 반환할 수 있는데 `LLM` Protocol은 `-> str`을 약속함

**증상**: (최종 리뷰에서 발견, 실사용 전 선제 수정) Ollama 응답의 `message.content`가 `None`이면 `analyzer.py`의 `json.loads(None)`이 잡히지 않는 `TypeError`를 던져, 재시도 로직을 완전히 우회했다.

**원인**: openai SDK의 `completion.choices[0].message.content` 타입이 `str | None`인데, `OllamaLLM.call()`이 이를 그대로 반환했다.

**해결**: `return completion.choices[0].message.content or ""`로 변경 — 빈 문자열은 기존 `JSONDecodeError` 재시도 경로로 자연스럽게 흘러간다 (commit `d544b96`).

### #3 `--json` 출력에서 참고용 고지 문구가 빠짐

**증상**: (최종 리뷰에서 발견) `python -m judgpt.analyze --json`으로 실행하면 REQUIREMENTS.md §4가 요구하는 "참고용 정보" 고지 문구가 전혀 출력되지 않았다.

**원인**: `run()`의 `--json` 분기가 `format_report()`를 거치지 않고 순수 JSON만 반환하는데, `DISCLAIMER`는 `format_report()` 안에서만 붙었다.

**해결**: `run()`은 순수 함수로 그대로 두고(스키마/테스트 계약 유지), `main()`에서 `--json`일 때 stdout에 JSON을 출력한 뒤 `DISCLAIMER`를 **stderr**로 추가 출력 — stdout은 여전히 기계가 파싱 가능한 순수 JSON으로 남는다 (commit `d544b96`).

### #4 Windows cp949 콘솔에서 리다이렉트 시 `UnicodeEncodeError`

**증상**: (최종 리뷰에서 실측 재현) `python -m judgpt.analyze --file chat.txt > result.txt`처럼 출력을 리다이렉트하면 고지 문구 앞의 `⚠️` 이모지가 cp949로 인코딩되지 않아 크래시했다. 대화형 콘솔에서는 재현되지 않아(Windows 콘솔은 UTF-16 I/O) 테스트로 못 걸렀다.

**해결**: `main()` 시작 시 `sys.stdout.reconfigure(encoding="utf-8")` 추가 (commit `d544b96`). 이후 PR #1 코드리뷰에서 **stdin에는 이 처리가 빠졌다는 추가 지적**을 받아 `sys.stdin`에도 `hasattr(sys.stdin, "reconfigure")`로 방어하며 `utf-8-sig`로 reconfigure 추가 (commit `754ca59`) — 테스트에서 `sys.stdin`을 `io.StringIO`로 monkeypatch하는 기존 테스트가 `reconfigure` 메서드가 없어 깨지지 않도록 `hasattr` 가드를 넣은 게 핵심.

### #5 `OllamaLLM.call()`이 `choices`가 빈 리스트일 때 `IndexError`

**증상**: (PR #1 코드리뷰에서 발견, 선제 수정 — 실제로는 아직 안 겪음) 프록시 오류나 컨텐츠 필터링으로 `completion.choices == []`가 오면 `completion.choices[0]`에서 잡히지 않는 `IndexError`가 나 날것 traceback이 사용자에게 보였다.

**해결**: `if not completion.choices: return ""` 가드 추가 — 빈 응답도 기존 재시도 경로로 흡수된다 (commit `754ca59`).

### #6 `--file ""`(빈 문자열)이 "파일 안 줌"과 동일하게 처리되어 stdin 대기로 빠짐

**증상**: (PR #1 코드리뷰에서 발견) `--file "$VAR"`를 스크립트로 넘길 때 `$VAR`가 비어있으면 에러 없이 조용히 stdin 읽기로 전환되어, 대화형 셸에서는 그냥 멈춘 것처럼 보였다.

**원인**: `if args.file:`이 빈 문자열을 falsy로 취급해 "파일 인자 없음"과 구분하지 못했다.

**해결**: `if args.file is not None:`으로 변경 — 빈 문자열이면 `open("")`이 `FileNotFoundError`를 던지고, 기존 "파일을 찾을 수 없습니다" 처리 경로로 자연스럽게 들어간다 (commit `754ca59`).

### #7 워크트리 삭제 후 빈 디렉토리가 남음 (Windows, OneDrive 동기화 추정)

**증상**: PR #1 병합 후 `git worktree remove`가 내부 파일은 전부 지웠지만 최상위 디렉토리(`​.claude/worktrees/judgpt-mvp`) 자체는 `Device or resource busy`로 지우지 못했다.

**원인**: 확실하지 않음 — OneDrive가 해당 폴더를 동기화 중이었거나 다른 프로세스가 핸들을 쥐고 있었을 가능성. git 메타데이터상으로는 워크트리 등록이 정상적으로 해제됨(`git worktree list`에 더 이상 안 뜸) — 빈 폴더만 남은 상태로 기능상 문제는 없음.

**해결**: 별도 조치 없이 방치 — 다음에 같은 디렉토리를 다시 쓰려고 할 때 지워지지 않으면, OneDrive 동기화가 끝난 뒤 재시도하거나 수동으로 지울 것.

### #8 워크트리 삭제 후 메인 저장소에서 `pytest`가 전부 `ModuleNotFoundError`류 수집 에러로 실패

**증상**: PR #1 병합 후 메인 저장소(`workspace/judgpt`)에서 `pytest`를 돌리니 8개 파일이 전부 수집 단계에서 에러가 났다.

**원인**: `pip install -e ".[dev]"`를 워크트리(`.claude/worktrees/judgpt-mvp`) 안에서 실행했었는데, editable install은 그 소스 경로로 링크를 건다. 워크트리를 지우고 나니 그 경로가 사라져 `judgpt` 패키지 자체를 못 찾게 됐다.

**해결**: 메인 저장소 루트에서 `pip install -e ".[dev]"`를 다시 실행 — editable install 경로가 메인 저장소로 갱신됨. **워크트리에서 병합 작업을 마치고 메인 저장소로 돌아올 때마다, 워크트리 안에서 `pip install -e`를 했었다면 메인 저장소에서 다시 설치해야 한다는 점을 기억할 것.**

### #9 `--json` 모드의 stderr 고지 문구가 cp949로 잘못 인코딩됨 (실제 Ollama로 수동 검증하다 발견)

**증상**: 실제 Ollama 설치 후 `python -m judgpt.analyze --file ... --json 2>err.txt`로 수동 검증하던 중, `err.txt`의 바이트가 UTF-8로 디코딩되지 않았다(`UnicodeDecodeError`). 유닛 테스트(`capsys` 기반)는 이 문제를 못 잡았다.

**원인**: #4에서 `sys.stdout`만 `reconfigure(encoding="utf-8")`했고, `--json` 모드의 `DISCLAIMER`를 출력하는 `sys.stderr`는 빠뜨렸다. 크래시는 안 났다 — 이 문구에 쓰인 한글 글자들이 cp949로도 인코딩 가능한 범위라 조용히 잘못된 인코딩(cp949)으로 써졌을 뿐이다(`⚠️` 이모지처럼 cp949 밖의 문자였다면 #4와 동일하게 크래시했을 것).

**해결**: `main()` 시작부에 `sys.stderr.reconfigure(encoding="utf-8")`을 `sys.stdout` 옆에 추가 (commit `3612e25`). **교훈: 콘솔 인코딩 문제는 크래시가 안 나도 잘못된 바이트가 조용히 써질 수 있으므로, stdout/stderr 둘 다 프로그램이 쓰는 모든 스트림에 동일하게 적용해야 한다 — 하나만 고치고 넘어가면 재발한다.**

## 법률 RAG 구현 (Task 1-8, 최종 리뷰, PR #2 후속 개선)

### #10 `fetch_statutes.py`도 stdout/stderr UTF-8 reconfigure가 빠져있었음 (#9와 동일 패턴, 재발)

**증상**: 실제 법제처 OC 키를 발급받아 `python -m judgpt.legal_data.fetch_statutes`를 처음 실행하니, 출력을 파일로 리다이렉트했을 때 `UnicodeDecodeError`가 났다(이번엔 #9처럼 "잘못된 인코딩이지만 크래시는 안 남"이 아니라, cp949로 인코딩 불가능한 바이트가 섞여 진짜 깨진 데이터가 써졌다).

**원인**: `analyze.py`의 `main()`에는 #4/#9로 `sys.stdout`/`sys.stderr` UTF-8 reconfigure가 다 들어갔지만, 같은 문제를 가진 별도 진입점인 `fetch_statutes.py`의 `main()`에는 애초에 이 처리 자체가 없었다 — CLI 진입점이 여러 개가 되면 한 곳에서 배운 교훈이 자동으로 다른 곳에 전파되지 않는다.

**해결**: `fetch_statutes.py`의 `main()` 시작부에도 동일하게 `sys.stdout.reconfigure(encoding="utf-8")` + `sys.stderr.reconfigure(encoding="utf-8")` 추가 (commit `8cc4d28`). **교훈: `if __name__ == "__main__":`으로 실행되는 진입점이 프로젝트에 여러 개면, 인코딩 reconfigure 같은 "진입점 공통 처리"를 체크리스트로 만들어 새 진입점을 추가할 때마다 확인할 것.**

### #11 법제처 API의 `lawSearch`(법령 검색)와 `lawService`(조문 원문)는 별개이고, `type=HTML`은 사람이 브라우저로 볼 iframe 래퍼만 반환함

**증상**: `fetch_statutes.py`의 `search_law()`(`target=law`, `lawSearch.do`)만으로는 "법이 존재한다"는 것만 확인되고, 실제 조번호·조문 제목(예: 형법 제311조가 정말 "모욕"이 맞는지)은 검증되지 않았다. 수동으로 `lawService.do?...&type=HTML`을 호출해봤더니 조문 내용이 아니라 `<iframe src="...lsInfoP.do...">` 하나만 든 빈 뷰어 페이지가 돌아왔다.

**원인**: `type=HTML`은 법제처 웹사이트에 사람이 붙여넣어 보는 뷰어 페이지용이다. 조문 단위 구조화 데이터가 필요하면 `type=XML`로 요청해야 `조문단위`/`조문번호`/`조문제목`/`조문내용` 태그가 담긴 실제 본문이 온다.

**해결**: 이 프로젝트의 `fetch_statutes.py`는 (Task 8 설계대로) `lawSearch`까지만 하고 나머지는 사람이 결과를 보고 판단하는 걸로 남겨뒀다 — 실제 조문 대조 검증은 이번에 `type=XML`로 수동 진행해 4개 법(형법/정보통신망법/성폭력처벌특례법/스토킹처벌법)의 인용 조번호를 전부 확인했다(`NEEDS_VERIFICATION = False`로 전환, commit `8cc4d28`). **`fetch_statutes.py` 자체를 조문 단위까지 자동 검증하도록 확장하고 싶다면, `type=JSON`이 아니라 `type=XML`을 쓰고 `조문단위` 태그를 순회해야 한다는 점을 기억할 것.**

## eval 하네스 (PR #3, 2026-09-17) 첫 실측 — exaone3.5:7.8b 베이스라인

### #12 `python -m judgpt.eval`로 실제 Ollama 첫 실측: 전체 F1 0.67, 협박 recall 0%

**증상**: PR #3 머지 후 골든셋 15건으로 `python -m judgpt.eval`을 처음 돌려봤다. 결과: 전체 Precision 0.78 / Recall 0.58 / F1 0.67. 유형별로는 명예훼손·모욕이 F1 1.00으로 완벽한 반면, **협박은 recall 0%(2건 모두 놓침)**, 성희롱도 recall 0%(2건 모두 다른 type으로 오분류)였다.

**원인 조사** (같은 케이스를 `analyze()`로 여러 번 반복 호출해 원인을 좁혔다):
1. **협박 케이스 중 "너희 집 어딘지 알아 조심해"(암시적 위협)는 8/8 시도 전부 탐지 자체가 안 됨.** `가만 안 둔다`(비교적 직접적인 위협 문구)는 노이즈는 있지만(약 60~70% 탐지) 최소 탐지는 됨. → 모델이 "가만 안 둔다" 류의 명시적 위협 어휘 없이 암시적으로 신변 위협을 가하는 표현은 잘 못 잡는다는 패턴으로 보인다. `prompt.py`의 `SYSTEM_PROMPT`에는 성적 발언/성희롱 구분 기준은 명시돼 있지만 협박에 대한 판단 기준(직접적 vs 암시적 위협 등)은 따로 없다 — 이게 원인일 가능성이 있다.
2. **`OllamaLLM.call()`(`judgpt/llm.py`)이 `temperature`를 지정하지 않는다** — Ollama/모델 기본값(보통 0.7~0.8대)을 그대로 쓰기 때문에 같은 입력도 실행마다 다른 결과가 나온다("가만 안 둔다" 케이스가 대표적). 이 때문에 이번 한 번의 실측 수치를 "모델의 절대적 정확도"로 못 박기는 어렵고, 특히 경계에 걸친 케이스는 여러 번 돌려봐야 신뢰도 있는 추세를 알 수 있다.
3. **성희롱(케이스 4, "한번만 만나줘 딱 한번만" — 거부 이후 반복)에서 모델이 스키마에 없는 `type: "거부 무시"`를 지어내 `AnalysisError`가 난 적이 있다.** 같은 케이스를 3번 돌리면 성적 발언 2번, 성희롱 1번으로 갈렸다 — "거부 이후 반복이면 성희롱"이라는 프롬프트의 구분 기준 자체는 모델이 어느 정도 인지하고 있지만(그래서 새 라벨을 지어내려는 시도까지 함), 정확히 `성희롱`이라는 지정된 라벨로 수렴을 못 하고 있다. **이번 PR #3의 `run_eval()` 케이스별 에러 격리 수정이 실전에서 바로 검증됨** — 이 스키마 밖 `type` 응답이 자동 재시도(analyzer.py)에서도 안 고쳐지면 `AnalysisError`가 나는데, 예전이었다면 전체 eval 실행이 죽었을 것.

**해결 (1차 — 협박은 해결, 성희롱은 미해결)**:
1. `OllamaLLM.__init__`에 `temperature: float | None = None` 옵션 추가(기본값 유지, `analyze.py` 실사용에는 영향 없음). `judgpt/eval.py`의 `main()`이 `llm`을 주입받지 않을 때만 `temperature=0`으로 `OllamaLLM`을 생성하도록 바꿔 eval 실측의 재현성을 확보했다.
2. `prompt.py`의 `SYSTEM_PROMPT`에 협박 판단 기준을 새로 추가: "명시적 위협 어휘가 없어도 거주지·직장 등 개인정보를 언급하며 신변 불안감을 조성하는 암시적 위협도 협박에 포함".
3. temperature=0으로 재측정한 결과: **협박 Precision/Recall/F1 전부 1.00으로 완전 해결**("너희 집 어딘지 알아 조심해" 포함 2건 모두 정탐). 전체 F1도 0.67 → 0.73로 개선.

**성희롱은 이번 수정 범위 밖이라 여전히 F1 0.00** — "거부 이후 반복" 케이스를 계속 성적 발언으로 오분류하거나 스키마 밖 type을 지어냄. 이건 후속 태스크로 남긴다(성희롱 전용 판단 기준을 더 구체화하거나, few-shot 예시를 프롬프트에 추가하는 방향 검토 필요).

`exaone3.5:7.8b` 대 `qwen2.5:7b` 비교는 아래 #13에서 진행.

### #13 `exaone3.5:7.8b` vs `qwen2.5:7b` 비교 (temperature=0 고정)

`docs/02-architecture.md` §10에 남아있던 "어느 모델이 더 나은지 미실측" 질문에 대한 답. `#12`의 프롬프트 수정(협박 암시적 위협 기준) 반영 후, 두 모델을 동일한 골든셋 15건·동일 프롬프트·`temperature=0`으로 각각 돌렸다(`python -m judgpt.eval` / `JUDGPT_MODEL=qwen2.5:7b python -m judgpt.eval`).

**전체 지표는 우연히 동일(둘 다 Precision 0.80 / Recall 0.67 / F1 0.73)하지만, 유형별 실패 패턴은 완전히 다르다:**

| 유형 | exaone3.5:7.8b | qwen2.5:7b |
|---|---|---|
| 명예훼손 | F1 0.67 (1/2건 놓침) | **F1 0.00 (2건 다 놓침)** |
| 모욕 | F1 1.00 | F1 1.00 |
| 성적 발언 | F1 0.80 (과탐지 1건) | **F1 1.00** |
| 성희롱 | F1 0.00 | F1 0.00 |
| 욕설 | F1 0.67 (1/2건 놓침) | **F1 1.00** |
| 협박 | **F1 1.00** | F1 0.67 (과탐지 2건) |

**qwen2.5의 협박 과탐지가 특히 문제적이다**: 케이스 3/4에서 피해자(B)가 거부 의사로 한 발언("그만 좀 해", "그만 연락하세요")을 협박으로 잘못 분류했다 — 단순 오탐이 아니라 **화자/대상을 혼동해 피해자의 발언을 가해 발언으로 뒤집어 씌운 것**이라 방향성이 거꾸로다. 실사용에 더 위험한 실패 유형으로 판단된다.

**결론**: exaone3.5는 명예훼손·협박에, qwen2.5는 욕설·성적 발언에 더 강하다. 어느 한쪽이 전반적으로 우월하다고 보기 어렵다. 기본 모델은 `exaone3.5:7.8b`로 유지 — 협박(신변 위협)을 놓치는 게 성적 발언을 놓치는 것보다 실사용 리스크가 크다고 판단. (이 표는 아래 #14의 성희롱 프롬프트 수정 **이전** 시점 — qwen은 그 수정 이후 재측정하지 않았다.)

### #14 성희롱(거부 이후 반복) 오분류 — 프롬프트 수정으로 부분 해결, 케이스 1건은 모델 한계로 확인

**증상**: `#13` 시점에 성희롱 F1이 두 모델 다 0.00이었다. `analyze()`를 직접 호출해 `temperature=0`으로 원인을 좁혔다.

**원인 조사**:
1. 골든 케이스 4("한번만 만나줘 딱 한번만")에서 모델은 `type: 성희롱`으로 **정확히** 분류했지만, 인용한 텍스트가 `"딱 한번만"`이라 골든의 기대 텍스트 `"한번만 만나줘"`와 부분 문자열이 안 겹쳐 매칭 실패로 처리됐다 — 모델 문제가 아니라 골든 데이터의 인용 구간이 너무 좁게 잡힌 문제.
2. 골든 케이스 3("에이 그래도 진짜 섹시한데")에서 모델은 `type: 성적 발언`으로 오분류했는데, `context` 필드에는 "B가 이전에 그런 말을 하지 말라고 요청했음에도 불구하고 계속해서..."라고 **성희롱의 정의를 정확히 추론**해놓고 있었다 — 추론은 맞는데 `type` 라벨만 못 고르는 패턴. 게다가 `prompt.py`의 "성적 발언: 반복 여부와 무관하게 발언 내용 자체로 판단한다"는 문장이 성희롱 정의의 "거부 이후 반복이면 성희롱"과 정면으로 모순돼 있었다 — 모델이 이 모순의 영향을 받았을 가능성이 있어 보였다.

**해결**:
1. 골든 케이스 4의 기대 텍스트를 `"한번만 만나줘"` → `"한번만"`으로 완화(모델이 실제로 인용하는 두 변형 모두를 포함하는 robust한 앵커로 교체) — 억지로 점수를 올리는 게 아니라 설계 원문(§2.1)이 명시한 "재인용 시 길이 차이 허용" 의도에 맞춘 것.
2. `prompt.py`의 성적 발언 정의를 "발언 내용 자체로 판단하되, 상대방의 거부 표현 **이후에** 나온 것이면 성희롱으로 분류한다"로 고쳐 성희롱 정의와의 모순을 제거.
3. 재측정(exaone3.5, temperature=0): **성희롱 F1 0.00 → 0.67, 전체 F1 0.73 → 0.82.** 케이스 4는 해결됐다.

**미해결로 확정**: 모순 제거 후에도 케이스 3은 그대로 `성적 발언`으로 나왔다(`context`는 여전히 거부-이후-반복을 정확히 서술하면서도). 문장으로 규칙·모순 제거까지 다 해봤는데도 `type` 선택이 안 바뀌는 걸 보면, 이건 프롬프트 지시 문제가 아니라 **exaone3.5:7.8b(7.8B 규모)가 "단일 성적 발언 → 성적 발언" 쪽으로 가진 고정된 편향**으로 보인다. **ponytail: 여기서 프롬프트 문장 수정 시도는 멈춘다 — 다음 단계는 few-shot 예시를 시스템 프롬프트에 추가하는 것(프롬프트 길이가 늘어나는 트레이드오프 있음), 필요해지면 시도할 것.**

### #15 골든 데이터셋 15건 → 24건 확장 후 재측정 — 명예훼손 recall 저하, 협박 암시적 위협의 일반화 실패 확인

**작업**: 유형별 다양성(같은 유형이라도 다른 문구), 다중 표현 케이스(한 대화에 서로 다른 유형 2개), 무해 대화 2건을 추가해 골든셋을 15건에서 24건으로 늘렸다(`judgpt/eval_data/golden.json`). `prompt.py`는 건드리지 않았다.

**재측정 결과**(exaone3.5:7.8b, temperature=0): 전체 Precision 0.80 / Recall 0.57 / F1 0.67 (24건). `#13`의 15건 기준(P 0.80/R 0.67/F1 0.73)보다 recall이 떨어졌는데, 원인은 새로 추가된 케이스의 어려움과 기존 케이스의 재현성 문제가 섞여 있다:

1. **명예훼손 기존 2건("회사 돈 횡령", "양다리")이 이번엔 둘 다 놓침(0/3, 새 케이스 포함)** — `analyze()`를 같은 입력으로 3번씩 반복 호출해도 매번 빈 결과라 이번 세션 안에서는 완전히 재현 가능하다(플레이키가 아님). 하지만 `#13`에서는 2건 중 1건은 잡혔었다(F1 0.67) — 프롬프트도 안 바꿨는데 결과가 달라진 것은, **`temperature=0`이라도 서로 다른 프로세스 실행 간에는 완전한 재현성이 보장되지 않을 수 있음**을 시사한다(CPU 추론에서 부동소수점 리덕션 순서가 실행마다 달라질 수 있는 등). 프롬프트에 명예훼손 전용 판단 기준이 따로 없다는 점(협박·성희롱·성적 발언에만 세부 기준이 있음)도 원인일 가능성이 있다 — 후속 조사 대상으로 남긴다.
2. **새 욕설 케이스("미친놈아")는 단독으로도, 협박과 같은 문장에 섞여도 전혀 탐지되지 않았다**(2/2 반복 재현). "시발"/"개빡치네"보다 어감이 약하게 학습됐을 수 있다 — 실제 모델의 recall 한계를 보여주는 유효한 신호로 보고 케이스를 그대로 둔다(더 "잘 잡히는" 단어로 바꿔 점수를 올리는 건 eval의 목적에 반한다).
3. **새 협박 케이스(직장 정보로 암시적 위협: "너 회사 어디 다니는지도 알아 조심하는 게 좋을걸")는 `#12`에서 고친 "거주지 언급 암시적 위협" 규칙이 일반화되지 않음을 보여준다** — 실제 위협 문장은 놓치고, 대신 피해자(B)의 반응 질문("지금 나 위협하는 거야?")을 협박으로 잘못 분류했다(2/2 재현). `#13`에서 qwen2.5 한정 문제로 봤던 "화자/대상 혼동" 패턴이 exaone3.5에서도 어려운 케이스에서는 나타난다는 뜻이다.
4. **새 성희롱 경계 케이스(거부 이후 반복된 "몸매는 진짜 죽인다")는 `#14`에서 이미 확정한 모델 한계(단일 성적 발언 편향)를 그대로 재현했다**(2/2, `성적 발언`으로만 분류) — 새로운 문제가 아니라 기존 한계의 재확인.

**결론**: 새 케이스들의 실패는 대부분 이미 알려진 한계(성희롱 편향, 암시적 위협 일반화 부족)의 재확인이거나 정직한 새 recall 신호(욕설 어감)라서 프롬프트를 추가로 손대지 않는다. 명예훼손의 재현성 저하는 원인이 명확하지 않아 별도 조사 없이 사실만 기록해둔다.

### #16 `## 예시`(few-shot) 섹션 추가로 협박·성희롱 F1 1.00 달성 — 첫 시도는 욕설 recall을 0으로 만들었지만, 예시를 다양한 유형으로 재구성해 해결

**시도**: `#12`/`#14`에서 이미 특정된 두 한계(협박 암시적 위협의 화자 혼동, 성희롱의 성적 발언 편향)를 겨냥해 `prompt.py`에 `## 예시` 섹션을 추가했다. 골든셋과 문구가 겹치면 "정답을 외운" 것처럼 보이므로 전부 새로 지어낸 문장을 썼다.

**1차 시도(예시 2개, 각각 협박 단독 / 성적발언+성희롱 조합만 다룸)**: 협박 F1 0.75→1.00, 성희롱 F1 0.50→1.00으로 목표는 달성했지만, **욕설이 4건 중 0건으로 완전히 무너졌다** — `"아씨 시발"`처럼 이전엔 항상 잡히던 케이스까지 3/3 반복 재현으로 놓치기 시작했다. 원인으로 추정한 것: 추가한 예시 2개의 출력이 전부 협박/성적 발언/성희롱만 사용해서, 모델이 in-context 예시로부터 "출력해도 되는 유형은 이 몇 가지"라는 암묵적 사전을 학습해 욕설·모욕 같은 미예시 유형의 출력 확률이 눌린 것으로 보인다(few-shot의 대표성 문제).

**2차 시도(예시 1을 욕설+협박 조합으로 재구성)**: 첫 번째 예시에 욕설 표현("미친놈아")을 협박 표현과 같은 대화에 함께 넣고, "한 대화에 서로 다른 유형의 표현이 여러 개 있을 수 있다"는 문장을 덧붙였다. 재측정 결과:

| 유형 | 원래 베이스라인(#15) | 1차 시도 | 2차 시도(최종) |
|---|---|---|---|
| 전체 F1 | 0.67 | 0.72 (욕설 붕괴) | **0.83** |
| 협박 | 0.75 | 1.00 | 0.89 (recall 1.00, 새 FP 1건 — 문장 일부를 중복 추출) |
| 성희롱 | 0.50 | 1.00 | **1.00** |
| 명예훼손 | 0.00 | 0.50 | 0.80 (의도한 타겟이 아니었는데 같이 개선됨) |
| 욕설 | 0.40 | **0.00(붕괴)** | 0.40 (베이스라인으로 완전 복구, 개선은 아님) |
| 모욕 | 1.00 | 0.67 | 1.00 |
| 성적 발언 | 0.80 | 0.75 | 0.80 |

2차 시도가 모든 유형에서 원래 베이스라인 이상이거나 동일해서(욕설만 베이스라인과 동일, 나머지는 개선) 이 버전으로 확정한다. 욕설 recall(0.40)은 few-shot 추가 전과 그대로라 **개선하지 못한 채 남아있다** — 이번 두 예시가 겨냥한 문제가 아니었고, 새 시도는 여기서 멈춘다.

### #17 욕설 전용 기준 + 3번째 few-shot 예시 추가로 F1 0.93 달성 — 성희롱은 기존에 알려진 한계로 다시 흔들림

**시도**: `#16`에서 못 고친 욕설 recall(0.40)을 별도로 겨냥했다. `prompt.py`의 "## 할 일" 1번에 욕설 전용 기준 문장을 추가하고("특정 대상을 향한 말이 아니라 감탄사처럼 혼잣말로 쓰인 경우도 욕설에 포함"), `## 예시`에 대상 없는 감탄사형 욕설("아 존나 짜증나네 진짜") 예시를 3번째로 추가했다. 골든셋 문구와 겹치지 않게 새로 지어냈다.

**재측정 결과**(Ollama 재시작 후 2번 연속 동일한 값 — 이번엔 프로세스 내 재현성 확인됨):

| 유형 | #16 확정본 | #17(최종) |
|---|---|---|
| 전체 F1 | 0.83 | **0.93** |
| 욕설 | 0.40 | **1.00** |
| 협박 | 0.89 | 1.00 |
| 명예훼손 | 0.80 | 1.00 |
| 모욕 | 1.00 | 1.00 |
| 성적 발언 | 0.80 | 0.80 |
| 성희롱 | 1.00 | **0.67** (케이스 3 재발 + 케이스 4 스키마 밖 type으로 분석 실패) |

성희롱만 내려갔는데, 원인은 새로운 문제가 아니라 **`#12`/`#14`에서 이미 문서화한 두 기존 한계가 그대로 재발한 것**이다: 케이스 3("진짜 섹시한데")은 `#14`가 "exaone3.5:7.8b의 고정된 편향"으로 확정한 바로 그 성적 발언 오분류이고, 케이스 4는 `#12`가 문서화한 "모델이 스키마 밖 type을 지어내는" 패턴(`"거부 표현"`)이다. few-shot 예시가 3개로 늘면서 원래도 불안정하던 이 두 케이스가 다시 흔들린 것으로 보인다.

**결론**: 전체 F1이 크게 개선됐고(0.67 → 0.93, 오늘 하루 동안) 성희롱 하락은 새 회귀가 아니라 기존에 받아들인 한계의 재발이라 이 버전으로 확정하고 멈춘다. 성희롱을 다시 회복시키려는 추가 시도는 `#14`의 결론(few-shot 대신 파인튜닝 등 더 무거운 개입이 필요할 수 있음)이 여전히 유효해서 진행하지 않는다.

### #18 `exaone3.5:2.4b`(1/3 크기)로 교체 검토 — 속도 35% 개선에 F1은 반토막, 기각

**배경**: GPU가 없는 환경(로컬/AWS CPU 인스턴스 모두 해당)에서 리플레이처럼 긴 입력을 분석하면 30초 타임아웃에 걸릴 수 있다는 문제를 논의하던 중, 더 작은 모델로 바꾸면 속도가 얼마나 개선되고 정확도가 얼마나 떨어지는지 실측을 요청받았다. 같은 계열(EXAONE 3.5)의 2.4B 버전을 받아 골든셋 24건·`temperature=0`으로 7.8B(현재 기본값)와 직접 비교했다.

**결과**:

| | `exaone3.5:7.8b`(기본값) | `exaone3.5:2.4b` |
|---|---|---|
| 전체 F1 | 0.93 | 0.53 |
| Precision | 0.90 | 0.42 |
| Recall | 0.95 | 0.70 |
| 24건 처리 시간 | 6분 43초(~17초/건) | 4분 23초(~11초/건, 약 35% 단축) |

**원인**: 파라미터가 1/3이어도 속도는 1/3이 되지 않았다 — CPU 추론은 고정 오버헤드(프롬프트 프리필 등)와 메모리 대역폭의 영향을 크게 받아 파라미터 수에 선형으로 비례하지 않는 것으로 보인다. 반면 정확도 손실은 훨씬 컸다: 특히 **완전히 무해한 대화 5건 전부에서 존재하지 않는 `기타` 유형 표현을 지어냈다**(예: "좋지", "고마워", "북한산" 같은 평범한 대화를 유해 표현으로 오탐). `[케이스 16]`은 스키마 밖 type(`"반박"`)을 지어내 분석 자체가 실패하기도 했다 — 이 문제는 7.8B에서도 나타나지만(`#12`, `#17`) 2.4B에서 빈도가 더 높았다.

**결론**: 속도 개선(35%) 대비 정확도 손실(F1 0.93→0.53, Precision은 절반 이하)이 너무 커서 기각한다. 특히 무해한 대화를 유해하다고 지어내는 건 이 도구의 신뢰도에 직접적인 타격이라 단순 속도-정확도 트레이드오프 이상의 문제로 본다. 기본 모델은 `exaone3.5:7.8b`를 유지하고, 긴 입력의 타임아웃 문제는 모델 축소가 아니라 다른 방향(청크 분할, GPU 인스턴스, 외부 LLM API 등)으로 풀어야 한다.
