# judgpt — 법률 RAG 설계 (v0.1, 2차 확장)

> 이 문서는 `docs/REQUIREMENTS.md` §3.2(법률 RAG)의 구체적인 구현 설계다. MVP(`docs/02-architecture.md`)는 이미 구현·리뷰·병합·실제 Ollama 검증까지 끝난 상태이며, REQUIREMENTS.md §3.2가 요구하는 "MVP가 안정화된 후" 조건을 충족했다고 보고 착수한다.

## 0. 범위 결정 (브레인스토밍에서 확정)

- **데이터 범위**: 조문(법제처 Open API, 완전 무료) + 소량 큐레이션 판례(수동 수집, 자동 대량 수집 아님) — 한국 판례 전문 DB는 대부분 유료라 예산 0원 제약상 대량 확보가 어렵다는 현실적 판단.
- **대상 법률**: 형법(모욕죄 제311조, 협박죄 제283조, 명예훼손죄 제307·309조), 정보통신망 이용촉진 및 정보보호 등에 관한 법률(온라인 명예훼손·협박 가중), 성폭력범죄의 처벌 등에 관한 특례법(통신매체이용음란 등 성희롱 관련) — REQUIREMENTS.md의 5가지 유해표현 카테고리(욕설/성희롱/협박/모욕/명예훼손)에 직접 연결되는 법만 우선 커버.
- **⚠️ 조문 번호는 재검증 필요**: 아래 §1의 매핑 표는 브레인스토밍 단계에서 기억에 기반해 초안으로 작성한 것이다. **구현 태스크에서 법제처 Open API로 실제 조문을 조회해 조번호·내용을 재확인하기 전까지는 확정된 법률 정보로 취급하지 않는다** — 이 프로젝트 자체가 "근거 없이 법률 정보를 지어내면 안 된다"는 원칙(REQUIREMENTS.md §4)을 지키려는 도구이므로, 설계 단계부터 이 원칙을 스스로도 지킨다.

## 1. 조문 매핑 (초안 — 구현 시 API로 재검증)

`judgpt/legal_data/articles.json`에 정적 매핑으로 저장한다. LLM이 지어내지 않고, 코드가 결정론적으로 조회한다.

| `type` | 기본 적용 법률 (초안) | 온라인/공개 채팅일 때 추가 (초안) |
|---|---|---|
| 모욕 | 형법 모욕죄 | 정보통신망법 관련 가중 조항 |
| 협박 | 형법 협박죄 | 정보통신망법 불법정보 유통 관련 조항 |
| 명예훼손 | 형법 명예훼손죄 | 정보통신망법 사이버 명예훼손 조항 |
| 성적 발언 | 성폭력처벌특례법 통신매체이용음란 관련 조항 | — |
| 욕설 | (모욕과 중복 시 모욕죄로 통합, 아니면 매핑 없음) | — |
| 협박·명예훼손·모욕 외 기타 | 매핑 없음 — "적용 가능 법률: 판단 근거 없음" | — |

- "온라인/공개 채팅 여부"는 `Expression.context`에 이미 LLM이 판단해 넣는 공개성 정보를 규칙에서 파싱하거나, 사용자가 CLI 인자로 명시(`--platform kakaotalk` 등, 구현 시 결정)하는 것 중 하나로 정한다 — 미해결 질문으로 남김(§7).
- 매핑에 없는 조합은 절대 LLM이 채우지 않는다 — "판단 근거 없음"을 명시적으로 반환한다(REQUIREMENTS.md §3.2).

## 2. 판례 큐레이션 데이터

`judgpt/legal_data/cases.json` — 리스트, 각 항목:

```json
{
  "case_id": "사건번호 (예: 대법원 2020도1234)",
  "court": "법원명",
  "summary": "사실관계·판단 요지 요약 (직접 조사해 작성, 원문 인용 아님)",
  "related_type": "모욕 | 협박 | 명예훼손 | 성적 발언",
  "source_url": "판례 원문을 확인할 수 있는 공개 출처 링크"
}
```

- **이 데이터를 실제로 채우는 작업은 구현 계획의 별도 태스크**로 둔다 — 지금 브레인스토밍 단계에서 판례를 즉흥적으로 만들어 넣으면 정확성 문제가 생기므로, 구현 시 실제 웹 리서치로 출처(`source_url`)와 함께 채운다. 출처를 확인할 수 없는 판례는 넣지 않는다.
- 초기 목표량: 카테고리(모욕/협박/명예훼손/성적 발언)당 2~3건, 총 10건 내외 — "소량 큐레이션" 범위에 맞춤. 부족하면 "관련 판례: 판단 근거 없음"으로 정직하게 표시하는 것이 잘못된 판례를 붙이는 것보다 낫다.

## 3. 파이프라인 — MVP 위에 별도 레이어

MVP의 `judgpt/analyzer.py`, `judgpt/schema.py`, `judgpt/llm.py`는 **건드리지 않는다**. 새 모듈이 MVP의 `AnalysisResult`를 입력으로 받아 보강한다.

```
AnalysisResult (MVP, 변경 없음)
  ↓
[judgpt/legal_rag.py] 각 Expression에 대해:
  ├─ (a) 조문 매핑 조회 (judgpt/legal_data/articles.json, 결정론적 조회, LLM 관여 없음)
  └─ (b) 판례 임베딩 검색 (judgpt/legal_data/cases.json 임베딩과 코사인 유사도, top-k)
  ↓
EnrichedExpression (Expression + applicable_laws + related_cases)
  ↓
EnrichedResult (AnalysisResult와 동일 구조 + 위 필드들)
  ↓
[judgpt/report.py 확장] "관련 법률 쟁점 / 판단 근거 / 관련 판례 / 추가로 필요한 자료" 섹션 추가 출력
```

**판단 이유 — 왜 MVP 스키마를 직접 확장하지 않고 별도 레이어로 감싸는가**: `AnalysisResult`/`analyze()`를 직접 바꾸면 MVP의 기존 테스트·CLI(`--json` 원본 출력 등)가 전부 영향을 받는다. 별도 레이어로 감싸면 MVP는 그대로 안정적으로 유지되고, RAG 레이어만 독립적으로 테스트·배포할 수 있다 — REQUIREMENTS.md §3.2도 "MVP 위에 얹는" 확장으로 명시하고 있다.

## 4. 임베딩

- 로컬 Ollama 임베딩 모델 사용 — 후보: `nomic-embed-text`(137M, 가벼움, CPU에서도 빠름). 판례 요약(`summary` 필드)만 임베딩한다 — 조문은 §1처럼 결정론적 매핑이라 임베딩이 필요 없다.
- 저장: 코퍼스가 수십 건 수준으로 작으므로 무거운 벡터 DB(Chroma 등) 없이 `judgpt/legal_data/case_embeddings.json`(벡터 배열)이나 SQLite 한 테이블로 충분 — 구현 시 더 간단한 쪽으로 결정.
- 검색: `Expression.context`(LLM이 이미 판단한 맥락 설명)를 쿼리로 임베딩해, 같은 `related_type`(또는 `type`)의 판례들과 코사인 유사도 top-k(예: 2~3건)를 반환.
- 관련 판례가 전혀 없거나 유사도가 임계값 미만이면 "관련 판례: 판단 근거 없음"을 반환한다 — 억지로 채우지 않는다.

**판단 이유 — 왜 조문은 규칙 기반, 판례만 임베딩인가**: 이번 범위(3개 법, 5개 카테고리)에서 `type`↔조문 관계는 사실상 고정이라 임베딩·유사도 검색을 붙이는 건 YAGNI 위반이다. 반면 판례는 "이 사안과 비슷한 판례"라는 질문 자체가 맥락(반복성·공개성 등) 의존적이라 의미 기반 검색이 실익이 있다.

## 5. 인터페이스 설계 (Protocol + Fake, MVP 패턴 재사용)

```python
class Embedder(Protocol):
    def embed(self, text: str) -> list[float]: ...

class FakeEmbedder:
    """테스트용. 준비된 벡터를 순서대로 반환."""
    ...

class OllamaEmbedder:
    """Ollama의 /api/embed 또는 OpenAI 호환 embeddings 엔드포인트 호출."""
    ...
```

MVP의 `LLM`/`FakeLLM`/`OllamaLLM` 패턴을 그대로 재사용 — 테스트는 실제 Ollama나 실제 임베딩 계산 없이 `FakeEmbedder`로 전부 검증한다.

## 6. 출력 형식 확장

CLI 리포트(`judgpt/report.py`)가 REQUIREMENTS.md §2의 최종 목표 포맷에 맞춰 다음 섹션을 추가한다(각 문제 표현 아래):

```
1. "..."
   유형: 모욕 / 대상: ... / 위험도: 높음
   적용 가능 법률: 형법 모욕죄 (제311조) [재검증 필요 — §0 참고]
   관련 판례: 대법원 20XX도XXXX (요지: ...) 또는 "판단 근거 없음"
```

`--json` 출력에도 `applicable_laws`/`related_cases` 필드가 추가된다. 기존 MVP 필드(`text`/`type`/`risk`/`target`/`context`)는 그대로 유지 — 하위 호환.

## 7. 미해결 질문

1. **"온라인/공개 채팅 여부"를 어떻게 판단할 것인가**: LLM의 `context` 판단에서 파싱할지, CLI 인자로 사용자가 명시할지 구현 시 결정.
2. **법제처 Open API OC 키**: 사용자가 직접 계정 가입 + 신청(승인까지 1~2일) 필요 — 구현 착수 전에 발급받아야 실제 조문 데이터를 채울 수 있다. 그 전까지는 조문 매핑 구조와 판례 임베딩 레이어를 OC 키 없이 먼저 구현·테스트 가능(FakeLLM/FakeEmbedder로).
3. **판례 큐레이션 실제 데이터 수집**: §2에서 언급한 대로 구현 계획의 별도 태스크(실제 웹 리서치 필요).
4. **벡터 저장 방식**: JSON+numpy vs SQLite — 구현 시 더 간단한 쪽으로 결정, 지금 확정하지 않음.
